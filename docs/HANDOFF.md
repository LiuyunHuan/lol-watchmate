## 1. 产品是什么，用户最在意什么

用户想要陪自己看 B站 LOL 比赛的朋友型助手，同时具备两个独立行为：

1. **正经问答**：用户通过语音或文字问 BP、阵容取胜条件、当前局势、选手历史数据。先给明确建议，再解释原因、条件与替代方案。详细内容放文字板，语音讲结论。不能只用“信息不足”敷衍，也不能在没有版本、阵容或数据依据时瞎给确定结论。
2. **主动玩梗**：选手死亡就可以接一句短梗，不需要证明他失误，更不必先完成战术分析。文字与语音都要有。可重复经典梗，但同一次死亡不得重复触发。

正经回答优先于娱乐。用户容忍正经回答延迟，不容忍为了死亡玩梗每次等待云端长分析；也不接受持续视频理解每秒几毛钱的成本。界面应像观赛助手，不要求用户理解内部调度才能使用。

用户偏好直接执行、修到可交付后再汇报，反感反复问“是否继续”。遇到真正缺失信息再问；不能用乐观描述掩盖尚未测过的能力。

## 6. 运行流程和时间规则

```text
用户授权窗口
  ├─ 每10秒单张JPEG → 云端视觉 → 比赛背景（不触发死亡）
  ├─ 每500ms尝试本地检测 → 身份/计时/击杀栏 → 去重与保护 → 短梗/缓存语音
  └─ 用户提问 → 请求新截图 → 场景 + 检索 + BO5文档 → 详细文字/语音结论
用户麦克风 → VAD/16kHz WAV → ASR → 同一问答链路
```

本地检测忙时跳过，不是每秒固定付费两次。数字统计约2秒读取一次，身份稳定后缓存；首次全英雄匹配和OCR准备较慢。问题截图有请求ID、时间戳与5秒获取超时，不能拿十秒前的旧截图当当下。

模型请求默认60秒（配置5～120秒），搜索25秒。周期视觉单飞，临时错误5～60秒退避；配置/鉴权类错误停止自动请求直到重新开始。暂停、换窗口、换局、新问题使用代次或取消机制，旧请求不能污染新状态。取消不保证服务端免费，费用回执仍可到账。

本地团战聚合窗口650ms，演示450ms。语音忙时文字照常追加；回答后只考虑未过期的一组梗。延迟测量应从用户画面首次有可辨认死亡证据开始，到音频真实开始播放结束，包含采样、识别、两帧、聚合与起播；不能只统计函数执行时间。

先将比赛区域归一到1920×1080，默认居中16:9，也可手动调整。1920×1200原图的上下黑边各60px，不要把原图坐标直接当比赛坐标。以下坐标是交接时实现速查，最终以源码为准，新增布局不要粗暴覆盖现有常量。

计分板左右各自从上到下：上单、打野、中单、ADC、辅助。团战横排从左到右：蓝方辅助、ADC、中单、打野、上单；红方上单、打野、中单、ADC、辅助。位置必须按这两套映射转换。

关键原则：

- 完整BP只限制本队候选集合。局内四位确认且只剩一位时可排除确认，来源标为 `draft-elimination`；不能将最终BP展示顺序硬绑角色。
- 手动锁定优先；遮挡可保留本局已确认英雄；首次未知不能按选手名猜。换局必须清缓存。
- `scene` 有可信时钟但不够HUD证据时，不把广告曲线当计分板。返回空选手更新，保留原统计。
- 灰色头像必须结合倒计时、KDA变化、受害者或稳定帧判断。黑白皮肤、变形和冷却数字不能直接视为死亡。
